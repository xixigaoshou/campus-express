# 第6部分 功能测试用例

> 项目：校园快递代取平台（赣南师范大学科技学院 Web 开发课程实训）
> 测试前置条件：后端（端口 8080）与前端（端口 5173）已正常启动，数据库已导入 schema_nobom.sql 与 02_notification_nobom.sql
> 预置测试账号（初始密码均为 `123456`）：需求发布者-小李（2024001）、接单者-小张（2024011，信誉分120）、小刘（2024012，信誉分105）、小赵（2024013，信誉分95）、小孙（2024014，信誉分75，低于80阈值）、小周（2024015，已禁用账号）

## 9.1 用户模块

| 用例编号 | 测试模块 | 测试步骤 | 预期结果 |
| --- | --- | --- | --- |
| TC-USER-01 | 用户注册 | 打开登录注册页，切换「注册」Tab，录入新学号、姓名、手机号、密码（≥6位）并提交 | 注册成功，弹出"注册成功，请登录"提示，自动切换到登录Tab，学号自动回填登录框 |
| TC-USER-02 | 用户注册 | 使用已存在的学号 `2024001` 注册，其余信息为新手机号 | 注册失败，后端返回"学号已注册"业务异常，页面弹出错误提示，不产生新用户 |
| TC-USER-03 | 用户注册 | 使用已存在的手机号 `13800000001` 注册，学号为全新学号 | 注册失败，后端返回"手机号已注册"业务异常，页面弹出错误提示，不产生新用户 |
| TC-USER-04 | 用户登录 | 输入正确学号 `2024001` + 密码 `123456`，点击登录 | 登录成功，弹出欢迎提示，跳转需求大厅；localStorage 写入 token；导航栏显示用户名、信誉分 |
| TC-USER-05 | 用户登录 | 输入正确学号 `2024001` + 错误密码 `000000` | 登录失败，返回"账号或密码错误"，停留在登录页，不产生 token |
| TC-USER-06 | 用户登录 | 输入已禁用账号 `2024015` + 正确密码 `123456` | 登录失败，返回"账号已被禁用，请联系管理员"异常，停留在登录页 |
| TC-USER-07 | 修改个人资料 | 登录后进入个人中心，修改宿舍区与手机号（格式正确），点击保存 | 资料更新成功，弹出提示；刷新页面后新资料正确回显；学号字段不可修改 |
| TC-USER-08 | JWT过期/401拦截 | 登录后手动把 localStorage 中的 token 篡改为过期/非法值，点击任意业务页面或发起接口请求 | 后端返回 401；前端 Axios 响应拦截器捕获 401，清除本地 token 与用户状态，自动跳转登录注册页 |

## 9.2 订单发布

| TC-PUB-02 | 修改待接单订单 | 在小李「我的发布-进行中」中找到一条「待接单」订单，点击编辑，修改送达地点与报酬后保存 | 修改成功，提示"修改成功"；订单详情中送达地点、报酬已更新，状态仍为「待接单」 |

| TC-PUB-04 | 接单后修改订单（禁止） | 小李发布订单后由小张抢单成功；小李再对该「已接单」订单发起修改 | 修改被拦截，返回"订单已接单，不允许修改"业务异常，订单信息不变（R-11） |

## 9.3 抢单接单场景

| 用例编号 | 测试模块 | 测试步骤 | 预期结果 |
| --- | --- | --- | --- |
| TC-TAKE-01 | 正常抢单 | 小张（2024011）登录，在需求大厅点击一条「待接单」订单的「抢单」按钮 | 抢单成功，弹出提示；该订单从需求大厅消失，进入小张「我的接单-进行中」，状态变为「已接单」 |
| TC-TAKE-02 | 并发抢单 | 小张、小刘、小赵同时对同一「待接单」订单发起抢单（可模拟两个浏览器/接口并发调用） | 只有一人抢单成功（乐观锁 version 匹配），其余人返回"该订单已被别人抢走，抢单失败"；订单 taker_id 只被成功者写入 |
| TC-TAKE-03 | 抢自己发布的订单 | 小李对自己发布的「待接单」订单点击抢单 | 被拦截，返回"不能接自己发布的订单"业务异常（R-8），订单仍为待接单 |
| TC-TAKE-04 | 信誉分低于80禁止接单 | 用小孙（2024014，信誉分75）登录并点击抢单 | 前端本地校验提示"信誉分低于80暂不可接单"，即使绕过前端直接调用接口，后端同样拦截返回信誉不足异常（R-23） |
| TC-TAKE-05 | 超出同时接单上限 | 使小赵（信誉95，普通等级上限2单）名下已有2单进行中订单，再对第3单发起抢单 | 被拦截，返回"超出同时接单上限"业务异常（R-9）；优秀等级（小张120）上限5单、良好等级（小刘105）上限3单同样生效 |

## 9.4 订单状态流转完整链路

| 用例编号 | 测试模块 | 测试步骤 | 预期结果 |
| --- | --- | --- | --- |
| TC-STATUS-01 | 完整状态链路 | 小李发布订单 → 小张抢单 → 小张更新为「取件中」→ 小张更新为「配送中」→ 小李点击「确认收货」 | 状态按 待接单→已接单→取件中→配送中→已完成 逐级流转；每一步页面弹出对应成功提示；终态为「已完成」 |
| TC-STATUS-02 | 禁止跨状态跳转 | 对「已接单」订单直接提交「已完成」，或对「待接单」订单直接提交「配送中」 | 被拦截，返回"订单状态不允许从X直接变更为Y"业务异常（R-1），状态不变 |
| TC-STATUS-03 | 只有发布者确认收货 | 小张（接单者）对配送中订单调用确认收货接口 /order/confirm-finish | 被拦截，返回"只有订单发布者可以确认收货"权限异常（R-3）；订单仍为「配送中」 |
| TC-STATUS-04 | 状态历史写入 | 完成一次完整状态流转后，查看订单详情页的状态变更历史 | 展示 5 条历史记录：待接单（发布）、已接单、取件中、配送中、已完成，每条含操作人与变更时间（R-2） |

## 9.6 超时业务模拟

| 用例编号 | 测试模块 | 测试步骤 | 预期结果 |
| --- | --- | --- | --- |
| TC-TIMEOUT-01 | 24h无人接单提醒 | 将一条待接单订单的 create_time 通过 SQL 改为 24 小时前，调用 simulateTimeoutCheck 模拟逻辑（生产环境为 @Scheduled 定时任务） | 系统向发布者生成一条站内通知："您的订单发布超过24小时仍无人接单，可调整报酬或取件地点"（R-14） |
| TC-TIMEOUT-02 | 接单后超时未取件 | 将一条「已接单」订单的接单时间改为超过2小时（120分钟），调用模拟超时检查 | 订单自动取消，接单者信誉分扣除（R-15），订单回到待接单/已取消，双方收到站内通知 |
| TC-TIMEOUT-03 | 送达后超时自动确认 | 将一条「配送中」订单的送达时间改为超过24小时，调用模拟超时检查 | 系统自动确认收货，订单置为「已完成」，报酬结算给接单者，双方收到站内通知（R-16） |
