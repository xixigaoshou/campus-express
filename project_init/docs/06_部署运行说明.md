## 7.2 后端部署启动步骤

### 步骤1：MySQL 8.0 准备，创建数据库 campus_express

1. 确认本机已安装 MySQL 8.0 并启动服务（Windows 服务名一般为 `MySQL80`）。
2. 使用命令行或 Navicat 连接 MySQL（本机账号 root）。
3. 数据库 `campus_express` 的创建与建表、初始化数据均包含在 SQL 脚本中，无需手动单独建库。

### 步骤2：执行建表 SQL、初始化测试数据 SQL

按顺序执行 `project_init/sql` 目录下的脚本（使用 Navicat 直接运行，或命令行执行）：

```
mysql -uroot -p < project_init/sql/schema.sql            -- 建库 + 核心表 + 索引约束 + 测试数据
mysql -uroot -p < project_init/sql/02_站内通知表.sql       -- 站内通知表 t_notification（辅助表）
mysql -uroot -p < project_init/sql/06_信誉分明细表.sql     -- 信誉分流水表 t_credit_log
mysql -uroot -p < project_init/sql/07_用户头像字段.sql     -- t_user.avatar 头像字段
mysql -uroot -p < project_init/sql/11_支付密码字段.sql     -- t_user.pay_password_hash 支付密码字段
mysql -uroot -p < project_init/sql/13_取件时间字段.sql     -- t_order.pickup_time 取件时间字段（并回填历史订单）
mysql -uroot -p < project_init/sql/14_评价唯一约束.sql     -- t_evaluation 唯一索引 uk_order_evaluator
```

- `schema.sql`：包含 `CREATE DATABASE campus_express`、核心表（t_user / t_order / t_order_status_history / t_order_transfer / t_message / t_evaluation / t_wallet / t_wallet_log）、全部索引与约束、测试订单数据。
- `02_站内通知表.sql`：站内通知表 t_notification（超时提醒、状态变更通知使用）。
- `13_取件时间字段.sql` / `14_评价唯一约束.sql` 都是幂等脚本（列/索引已存在时跳过），可重复执行。
- 若 `schema.sql` 已包含 `pickup_time` 与 `uk_order_evaluator`（当前基线已包含），这两步执行时为空操作，仅为兼容旧库保留。
- 执行成功后，t_user 中有 8 个预置账号，t_order 中有 10 条多状态订单。

### 步骤3：修改 application.yml 数据库连接账号密码

打开 `campus-express-backend/src/main/resources/application.yml`，将数据源部分改为本机 MySQL 的账号密码：

```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/campus_express?useUnicode=true&characterEncoding=UTF-8&serverTimezone=Asia/Shanghai&useSSL=false&allowPublicKeyRetrieval=true
    username: root        # 改为你的 MySQL 用户名
    password: "123456"    # 改为你的 MySQL 密码
```

> 注意：JWT 密钥、业务规则参数（信誉分阈值、超时时间、接单上限等）也在此文件中配置，可按下发需求调整，无需改代码。

### 步骤4：IDEA 打开后端 Maven 项目，刷新依赖

1. 使用 IntelliJ IDEA 打开 `campus-express-backend` 文件夹（**直接打开项目根目录，不是父目录**）。
2. 等待 Maven 自动导入依赖（pom.xml 已配置 spring-boot-starter-web、mybatis-plus、jjwt、spring-security-crypto 等）。
3. 若依赖未自动导入：右键 pom.xml → Maven → Reload Project（刷新按钮）。

### 步骤5：启动主类，后端端口 8080

1. 找到主启动类 `CampusExpressApplication.java`（路径 `com.campus.express` 包下）。
2. 点击 Run 启动，观察控制台日志出现 `Started CampusExpressApplication`，端口 8080。
3. 若 8080 被占用：修改 application.yml 中 `server.port` 或关闭占用进程。

### 步骤6：验证

1. 接口验证：浏览器访问 `http://localhost:8080/api/user/login`（POST），或直接启动前端后从页面登录。
2. 接口文档：完整接口清单见 `project_init/docs/04_API接口文档.md`（统一前缀 /api）。
3. 测试账号：使用 7.4 节预置账号登录验证。

## 7.3 前端部署启动步骤

### 步骤1：进入 campus-express-frontend 目录

```
cd campus-express-frontend
```

### 步骤2：安装依赖

```
npm install
```

> 建议 Node.js 版本 ≥ 18。若安装缓慢可切换淘宝镜像源：`npm config set registry https://registry.npmmirror.com`。

### 步骤3：启动前端

```
npm run dev
```

启动成功后控制台输出 `Local: http://localhost:5173/`，浏览器访问 **http://localhost:5173** 即可进入系统登录页。

### 步骤4：Vite 代理说明（跨域处理）

前端所有请求走统一前缀 `/api`，Vite 开发服务器通过代理转发到后端，避免浏览器跨域拦截：

```js
// vite.config.js
server: {
  port: 5173,
  proxy: {
    '/api': {
      target: 'http://localhost:8080',   // 后端地址
      changeOrigin: true
    }
  }
}
```

- 前端请求 `/api/user/login` → 代理转发 → 后端 `http://localhost:8080/api/user/login`。
- 生产部署时，由 Nginx 等反向代理将 `/api` 转发到后端，或后端开启 CORS。

## 7.5 常见问题故障排查

### 问题1：Invalid bound statement（Mapper SQL 找不到）

- **现象**：启动或调用接口报 `Invalid bound statement (not found): com.campus.express.mapper.XXXMapper.xxx`。
- **原因**：Mapper 接口方法在对应 XML 中缺少同名 `id`，或 XML 未被打包到 classpath。
- **排查**：
  1. 检查 `OrderMapper.xml` 等 XML 文件是否放在 `src/main/resources/mapper/` 目录（与 application.yml 中 `mybatis-plus.mapper-locations: classpath:mapper/*.xml` 一致）。
  2. 检查 XML 的 `namespace` 是否与 Mapper 接口全限定名完全一致。
  3. 检查接口方法名、参数名（@Param）与 XML 的 `id`、`#{参数}` 是否对齐。
  4. Maven 重新编译：`mvn clean compile` 后重启。

### 问题2：401 未登录，token 失效

- **现象**：接口返回 401，前端跳转登录页；或注册/登录接口本身报 401。
- **排查**：
  1. 注册/登录接口必须在 `WebMvcConfig` 中配置为放行路径：`/api/user/register`、`/api/user/login`（拦截器校验 token 时跳过这两条）。
  2. 请求头格式必须为 `Authorization: Bearer <token>`（与 JwtUtil 校验逻辑一致），前端 Axios 拦截器已自动注入。
  3. token 有效期 7 天（application.yml `jwt.expire-minutes: 10080`），过期后需重新登录，前端响应拦截器捕获 401 自动清除 token 并跳转登录页。

### 问题3：跨域报错

- **现象**：浏览器控制台报 `Access to XMLHttpRequest ... blocked by CORS policy`。
- **排查**：
  1. 开发环境必须通过 Vite 代理访问后端（`/api` → `http://localhost:8080`），不要直接请求 `http://localhost:8080`，代理配置见 7.3 步骤4。
  2. 前端请求必须统一使用 `/api/xxx` 相对路径（Axios baseURL 为 `/api`），不要写死完整后端地址。
  3. 若前后端分机器部署，需后端配置 CORS 或使用 Nginx 反向代理解决。

### 问题4：乐观锁抢单失效，多人抢到同一个订单

- **现象**：同一订单被多个接单者同时抢到。
- **排查**：
  1. 抢单必须走 `OrderMapper.optimisticTakeOrder` 的 SQL，更新条件必须包含：`status = '待接单' AND version = #{version}`。
  2. 调用方必须把**查询时读到的 version** 传入更新语句（前端流程为：查订单详情拿到 version → 抢单时回传），不能传空或固定值。
  3. 抢单方法必须加 `@Transactional` 且为**独立的 Service 方法调用**（避免同类内部调用导致事务/乐观锁代理失效）。
  4. 判断更新行数：返回 0 行代表 version 已被其他线程抢先递增，必须抛出"该订单已被别人抢走"业务异常。
  5. 验证方式：查询 t_order 的 version 字段，每抢单成功一次 +1。

### 问题5：订单状态可以跨状态跳转

- **现象**：订单状态直接从「待接单」变成「已完成」等跨级跳转，未被拦截。
- **排查**：
  1. 状态流转必须统一走 `OrderServiceImpl.updateOrderStatus`，内部校验状态机（待接单→已接单→取件中→配送中→已完成）与终态规则（已完成/已取消不可再流转）。
  2. 前端不要直接调用发布/取消接口之外的方式改状态；发布、抢单、取消等操作内部也需写入状态历史，确保 `t_order_status_history` 每次变更都有记录。
  3. 确认收货（置「已完成」）接口 `/api/order/confirm-finish` 只允许订单发布者调用（R-3）。

### 问题6：前端页面空白、路由不跳转

- **现象**：打开 http://localhost:5173 页面空白，或登录后停留在登录页不跳转。
- **排查**：
  1. 确认依赖安装完整：`npm install` 后检查 node_modules 是否存在，缺失时删除 node_modules 与 package-lock.json 重新安装。
  2. 路由守卫（`src/router/index.js`）：未登录访问业务页会重定向 `/login`；登录后访问 `/login` 会重定向 `/hall`，若 token 校验逻辑异常会造成死循环，检查 `stores/user.js` 中 token 读写。
  3. 浏览器控制台查看报错：确认后端已启动（接口 404 会导致页面数据加载失败）。
  4. 路由跳转需在登录成功拿到返回数据后再 `router.push('/hall')`，确认 axios 返回结构解析与 `Result<T>` 封装一致（`data` 字段取值）。
  5. 端口占用：5173 被占用时 Vite 会自动换端口，以控制台实际输出为准。
