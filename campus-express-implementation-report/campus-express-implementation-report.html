校园快递代取平台 系统功能实现报告

本报告完整记录系统的功能实现情况：前后端分离架构下，用户管理、订单发布与抢单、订单状态机流转、 留言消息、双向评价、信誉分机制、站内通知、订单筛选与头像上传等模块均已完成并验证， 核心业务规则（乐观锁抢单、状态机约束、角色权限控制、超时自动处理）全部落地。

系统：校园快递代取平台（campus-express） 架构：Spring Boot + Vue 3 前后端分离 日期：2026-10-03

01 系统概览与核心结论

系统是一个面向校园场景的快递代取撮合平台：需要代取快递的同学发布需求并设置报酬， 有空闲的同学在需求大厅抢单接单，双方通过订单留言沟通，完成后互评；平台用信誉分约束双方履约行为， 用站内通知串联关键业务节点，并实现了两段式收货、超时自动结算等完整闭环。

03 用户管理模块

用户模块覆盖注册、登录、资料维护、密码安全与头像上传，并通过 canPublish 字段实现 「发布者 / 接单者」两种角色的权限划分——两个角色不是两套账号体系，而是同一账号身份下的功能权限控制。

3.1 注册与登录

  • ✓
    注册（POST /api/user/register，公开接口） 学号、手机号唯一性校验（重复直接拒绝）；密码经 BCrypt 加盐哈希存储，杜绝明文；新用户初始化信誉分 100、账户状态正常、默认 canPublish=false（接单者角色），发布权限需管理员开启。
  • ✓
    登录（POST /api/user/login，公开接口） 支持学号或手机号 + 密码登录，BCrypt matches 比对密码；账号被禁用（status=0）直接拒绝；登录成功签发 JWT 无状态令牌，返回 token + 用户信息（含 canPublish），前端持久化到 localStorage。
  • ✓
    获取当前用户信息（GET /api/user/info） 从 JWT 解析身份返回用户信息，密码哈希字段脱敏（置 null）后返回，保证安全。

3.2 密码安全：修改与找回

  • ✓
    修改密码（PUT /api/user/password，需登录） 必须校验原密码正确（BCrypt 比对），新密码长度 6~20 位且不可与原密码相同，更新为新的 BCrypt 哈希，防越权修改。
  • ✓
    找回密码（POST /api/user/password/reset，免登录） 学号 + 注册手机号双重匹配验证身份后才能重置；验证失败统一提示「学号或手机号信息不匹配」，避免泄露账号是否存在（防账号枚举）。

3.3 个人资料与头像上传

  • ✓
    更新资料（PUT /api/user/info） 仅允许修改手机号（唯一校验，排除本人）与宿舍区域，学号不可修改；发布者保存的个人信息可在发布需求时直接引用。
  • ✓
    头像上传（POST /api/user/avatar，需登录） 仅允许 jpg / jpeg / png / gif / webp 格式，大小不超过 5MB；文件用 UUID 重命名保存至项目 uploads/avatar/ 目录，杜绝重名与路径穿越；返回可访问相对路径 /uploads/avatar/xxx。
  • ✓
    头像访问链路 后端 WebMvcConfig 将 /uploads/** 映射到本地目录，并在 JWT 拦截器中放行该路径（img 标签加载无 token 场景）；前端 Vite 同时代理 /uploads 转发，确保各端展示正常。
角色权限设计： 同一账号通过 canPublish 布尔值区分身份——发布者（true）可发布需求、不可抢单，顶部菜单显示「发布需求」、隐藏「需求大厅」； 接单者（false）可抢单、不可发布，菜单显示「需求大厅」、隐藏「发布需求」。页面菜单（v-if）与接口层双重校验，直接输入 URL 也无法越权。

04 订单管理模块（系统核心）

订单模块实现了从发布、抢单、状态流转到两段式收货、超时自动处理的完整业务闭环， 是系统最核心的部分，业务规则全部在 Service 层以事务方式落地。

4.1 订单发布

  • ✓
    发布需求（POST /api/order/publish） 填写快递公司、快递单号、取件地点、送达地点、期望时间、备注与报酬；报酬金额受规则约束（0.5 ~ 50 元，R-17）；仅 canPublish=true 用户可发布（接口层二次校验角色）；新单初始化乐观锁 version=0、状态「待接单」，并写入首条状态历史「需求发布，进入待接单」。
  • ✓
    修改订单（PUT /api/order/update-wait） 仅发布者本人可操作，且仅「待接单」状态允许修改；订单被接单进入业务流转后禁止修改核心字段（R-11）。

4.2 抢单接单：乐观锁 + 事务（R-6 ~ R-10）

抢单是并发热点，采用乐观锁 + 数据库事务保证同一订单只能被一人成功承接：

抢单校验规则（全部通过才执行更新）
规则校验内容实现方式
R-6订单必须处于「待接单」状态读取后状态比对，已接单直接拒绝
R-7并发冲突保护（同一订单只被一人抢到）UPDATE ... SET status='已接单', version=version+1 WHERE order_id=? AND status='待接单' AND version=读取值；更新行数为 0 即抢单失败，提示「手慢了」
R-8禁止接自己发布的订单发布者 ID 与当前用户比对
R-23信誉分低于阈值（80）禁止接单credit_score 与配置阈值比对
R-9同时进行中订单数不超过信誉等级上限统计本人进行中订单数，与等级上限（优秀 5 单 / 良好 3 单 / 普通 2 单）比对

抢单成功后写状态历史（待接单 → 已接单，记录操作人），并向发布者推送通知「您的订单已被 xxx 接单」（R-5）。 整个抢单过程在 @Transactional 事务中完成，避免数据不一致。

4.3 订单状态机（R-1 ~ R-5，硬性约束）

状态流转严格按状态机执行，禁止跨状态跳转；任何一次变更都必须写入 t_order_status_history 历史表，并在变更后通知相关方。

状态流转与权限对应关系
状态变更触发操作允许的操作人
待接单 → 已接单抢单接单接单者（canPublish=false），乐观锁保证唯一
已接单 → 取件中开始取件仅接单者本人
取件中 → 配送中开始配送仅接单者本人
配送中 → 待收货确认送达（记录 confirm_arrival_time 计时）仅接单者本人
待收货 → 已完成确认收货 / 2 小时超时自动确认仅发布者本人；超时由定时任务自动完成并结算报酬
待接单 → 已取消取消订单发布者无条件取消
已接单/取件中 → 待接单接单者取消接单者，扣信誉分 5，退回大厅重新开放

4.4 取消订单规则

  • ✓
    待接单：发布者无条件取消 订单直接置为「已取消」终态，写状态历史。
  • ✓
    已接单 / 取件中：接单者取消需付出代价 接单者取消 → 信誉分扣 5（写 t_credit_log 流水明细）→ 订单退回「待接单」重新开放 → 通知发布者「订单已被接单者取消，重新进入待接单」。
  • ✕
    配送中及之后：禁止取消 处于履约中后段（配送中 / 待收货）不允许取消，保证交易稳定。

4.5 两段式确认收货与超时自动处理

两段式收货设计（用户需求）

接单者确认送达后订单进入「待收货」并记录送达时间；发布者须在 2 小时内确认收货，报酬才会结算给接单者； 若超时未手动确认，定时任务（@Scheduled 每 60 秒扫描）自动确认收货，报酬照常结算——既保证接单者及时拿到报酬，也约束发布者及时验收。

超时任务处理场景（R-14 ~ R-16）
场景触发条件系统动作
发布超时无人接单（R-14）待接单超过 24 小时仅提醒发布者调整报酬或时限，不自动取消
接单后超时未取件（R-15）已接单超过 2 小时未更新取件中自动取消 + 扣接单者信誉分 5 + 退回待接单 + 通知发布者
送达后超时未确认（R-16）待收货超过 2 小时（以 confirm_arrival_time 为计时起点）系统自动确认收货置为「已完成」，报酬结算给接单者，双方收到通知

4.6 需求大厅：分页 + 筛选搜索

  • ✓
    大厅分页（GET /api/order/hall-page） 仅展示「待接单」状态订单，按发布时间倒序；MyBatis-Plus 分页插件支持 pageNum / pageSize。
  • ✓
    多字段模糊搜索 关键词动态拼接 SQL，模糊匹配快递公司、快递单号、取件地点、送达地点、备注五个字段（空串自动归一化为 null 避免无意义过滤）。
  • ✓
    报酬范围过滤 minReward / maxReward 参数按报酬区间筛选；前端筛选栏含关键词输入框、报酬上下限、查询与重置按钮，筛选后自动回到第一页。

4.7 我的订单与订单详情

  • ✓
    我的发布 / 我的接单（分页接口） /api/order/my-publish-page 与 /api/order/my-take-page 分别按发布者、接单者维度查询，支持「进行中 / 历史」状态分组过滤；前端按角色只展示对应 tab（发布者只见「我的发布」，接单者只见「我的接单」）。
  • ✓
    订单详情（GET /api/order/{orderId}） 一次性返回：订单完整信息 + 发布者/接单者昵称（用户关联查询）+ 完整状态流转历史 + 双向评价列表，供详情页集中展示。

05 留言消息模块

留言以订单为会话维度，发布者与接单者围绕某一笔订单沟通取送细节； 支持未读标记、会话列表与角标轮询，并包含敏感词过滤。

  • ✓
    发送留言（POST /api/message/send） 仅订单参与者（发布者或接单者）可发送，越权返回 403；接收者自动定位为另一方；订单未接单（无接单者）时禁止留言；内容经内置敏感词过滤，命中词替换为 *；新消息默认未读。
  • ✓
    会话消息分页（GET /api/message/order-page/{orderId}） 按发送时间升序返回，MessageVO 关联查询发送者昵称展示；会话隐私控制——仅参与者可查看该订单留言。
  • ✓
    已读标记与未读数 进入会话标记该订单下发给我的消息全部已读；/api/message/unread-count 提供全局未读总数做导航角标。
  • ✓
    会话列表（GET /api/message/conversations） 返回我参与的所有订单会话，含对方昵称、未读数与最新一条消息，按最新消息时间倒序——解决「红点不知道是哪个订单的消息」问题：点进具体会话即可定位订单，进入后角标消失。
  • ✓
    前端轮询 消息角标每 5 秒轮询更新，点击会话跳转对应订单详情并自动标记已读，角标实时减少。

06 评价与信誉分体系

6.1 双向评价（R-21）

  • ✓
    创建评价（POST /api/evaluation/create） 四重校验：① 仅订单发布者或接单者可评价（越权拦截，修复了历史越权漏洞）；② 订单必须「已完成」；③ 订单完成 7 天内有效，过期不可评；④ 同一用户对同一订单只能评价一次（双方互评，不可重复刷分）。
  • ✓
    评价列表（GET /api/evaluation/list/{orderId}） 返回该订单全部双向评价，EvaluationVO 关联查询评价人 / 被评价人昵称；订单详情页展示。

6.2 信誉分机制（R-22 ~ R-24）

信誉分增减规则与等级
场景分值变化说明

  • ✓
    信誉分接口（GET /api/user/credit-logs） 仅返回本人流水，按时间倒序分页；分值更新带条件防负数（updateCreditScore 内校验），更新失败提示「信誉分不足」。

  • ✓

13 虚拟钱包模块（R-25 ~ R-28）

在原有 7 张表（t_user / t_order / t_order_status_history / t_message / t_evaluation / t_credit_log / t_notification）零改动的基础上增量新增虚拟钱包模块： 新增 t_wallet（用户钱包）与 t_wallet_log（资金流水）两张表，实现模拟充值（不接入真实支付）与订单报酬的 冻结 → 结算 / 解冻全流程。所有资金操作（充值 / 冻结 / 解冻 / 结算）一律写入资金流水，保证每笔变动可追溯； 资金变更与订单状态变更共用同一事务（冻结 / 解冻 / 结算方法不新建事务，由订单服务在 @Transactional 内调用），任一步骤失败整体回滚。

新增数据表

表名关键字段说明
t_walletuser_id（唯一，外键 t_user，级联删除）、balance（可用余额，默认 0.00）、frozen_balance（冻结余额，默认 0.00）用户钱包；注册自动创建零余额钱包；预置测试账号手动初始化余额（小李/小王 100、小陈 5、小张/小刘 50、小赵 10、小孙 5、小周 0）
t_wallet_loguser_id、related_order_id（可空，外键 t_order，SET NULL）、log_type（1充值 2冻结 3解冻 4结算收入 5支出扣减）、amount（正负）、before/after_balance、before/after_frozen、remark资金流水；充值场景 related_order_id 为空；每次资金变动记录变动前后可用余额与冻结余额

注：功能上线前的历史订单不追溯冻结 / 结算资金，流水明细自模块上线后的新操作开始记录。

业务规则 R-25 ~ R-28

规则内容实现位置
R-25发布订单前校验发布者钱包可用余额 ≥ 订单报酬，余额不足禁止发布前端发布页余额提示 + 提交禁用；后端 WalletServiceImpl.freezeBalance 余额校验
R-26订单发布成功，报酬金额从可用余额转入冻结余额，冻结资金不可重复消费订单入库前调用 freezeBalance（同一事务，失败回滚订单）
R-27订单取消（待接单 / 接单中途取消），冻结报酬自动解冻返还发布者可用余额OrderServiceImpl.cancelOrder 两个取消分支调用 unfreezeBalance（返还对象为发布者）
R-28订单成功履约变更为已完成，冻结报酬扣减并转入接单者可用余额，生成双方资金流水手动确认收货（confirm-finish）、超时模拟、定时自动确认收货三处均调用 settleOrderReward

后端实现

  • 枚举 WalletLogType：RECHARGE(1) / ORDER_FROZEN(2) / ORDER_UNFROZEN(3) / ORDER_INCOME(4) / ORDER_PAY(5)，提供 code ↔ 文本转换，VO 层展示流水类型文本
  • 实体 / Mapper：Wallet、WalletLog 继承 MyBatis-Plus BaseMapper；WalletMapper.xml 提供 freeze / unfreeze / settlePayFrozen / settleIncome / recharge 五个条件更新（balance ≥ amount、frozen_balance ≥ amount），并发下防超扣
  • DTO / VO：WalletRechargeDTO（充值金额 0.5 ~ 100 元，JSR-303 校验）；WalletVO（可用 / 冻结余额）；WalletLogVO（流水文本 + 变动前后双余额 + 关联订单 + 备注）
  • 服务：WalletService.freezeBalance / unfreezeBalance / settleOrderReward / recharge / getWalletInfo / pageWalletLogs；资金操作方法不新建事务，共用订单服务外部事务；recharge 独立事务
  • 订单服务接入：publishOrder（冻结）、cancelOrder 两分支（解冻）、完成结算三处（手动确认 / 超时模拟 / 定时任务）
  • 注册接入：UserServiceImpl.register 插入用户后自动创建零余额钱包（balance=0.00, frozen_balance=0.00）
  • 防御性兜底：unfreezeBalance 幂等（冻结余额已为 0 时静默返回，避免「接单者取消解冻后退回待接单、发布者再次取消」重复解冻报错）；settleOrderReward 结算前若检测到该订单存在解冻流水（资金已返还），先重新冻结再结算，保证「取消后退回待接单 → 再次被接单完成」的资金闭环（R-27/R-28 衔接）
